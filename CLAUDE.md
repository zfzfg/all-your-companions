# CLAUDE.md — All your Companions

### *All your Companions — in one place!*

Unified VS Code and Cursor sidebar client for **Google Antigravity CLI (Gemini)**, **xAI Grok Build**, **OpenAI Codex**, and **Anthropic Claude Code**, driven through native ACP adapters. Decoupled from external remote control relay architecture to focus 100% on editor-native capabilities: local-first execution, privacy, universal diff inspection and one-click revert across all AI providers, git worktree isolation, and voice control.

## Status

See [CHANGELOG.md](CHANGELOG.md) for the current version and full release history (the Marketplace/GitHub-published build can lag the local working tree). The whole test suite is **binary-free** — CI uses fake Grok and Codex ACP fixtures; binary-dependent probes live separately in `research/*.cjs`. Grok Plan mode is enabled and enforced by the client safety gate (see `research/plan-mode.md` § Resolution); Codex plan review is an ordinary permission whose `allow_once` means implement — write/shell enforcement stays in the adapter/CLI, and Auto accept is suppressed by `effectivePlanActive`. Between the plan gate and Auto accept / the card, `decidePermission` in `src/permission-rules.ts` applies persistent allow/ask/deny rules (tool × command-prefix × path-glob). Deny always wins, then last-match-wins; a built-in safety floor (delete on system paths, writes to credential files) cannot be overridden. Empty user rules fall through to today's card / Auto accept. Checked-in `.grok/permissions.json` stays inert until adopted. Smoke-tested end-to-end on Linux, Windows-via-WSL, and the **native Windows build** (`irm https://x.ai/cli/install.ps1 | iex`) — `cli-locator` resolves `grok.cmd`/`grok.exe` and `terminal-manager` runs Grok-delegated commands under PowerShell on Windows (`pwsh`→`powershell`, mirroring the standalone CLI; #46), `$SHELL` (else `/bin/sh`) on POSIX.

This file is the project map: it describes the **current** architecture, not a per-version log.

**Editing discipline — keep this file lean.** When behavior changes, *rewrite* the affected lines to the new current state; do **not** append a note about what changed or why the old way was wrong. Concretely, none of these belong here:
- version-by-version history or "fixed in 0.2.x / removed in 1.4.x" → [CHANGELOG.md](CHANGELOG.md);
- bug post-mortems / "used to… / this broke because…" narrative → a code comment or `research/*.md`;
- evidence dumps ("one capture: 17.7s", "a real case: 74 messages") → `research/*`.

State the rule, name the function / constant / config-key an agent would grep for, and link the deep-dive — **one fact, one home**. Every feature already has a `research/*.md`; `docs/architecture.md` holds the event-flow detail; [docs/internal/ACP-feedback.md](docs/internal/ACP-feedback.md) is the upstream-facing summary of grok-CLI/ACP friction, agent-family wire differences, and our workarounds (update it when a new workaround lands or an old one becomes obsolete). If a paragraph explains *how we found* a bug rather than *how the code behaves now*, it's in the wrong file.

**Grok CLI compatibility.** The extension updates the CLI once per extension upgrade (`maybeUpdateCliOnUpgrade`), then probes `grok --version` each start (`resolvePlanModeAvailability`) to decide whether Plan mode is offered. A live, verified-old CLI latches Plan off for that session; an unreadable probe disables it but stays **re-checkable**, so picking Plan retries without a restart. The floor is `GROK_REQUIRED_VERSION`; known-broken Windows startup ranges are handled by `isStdioBrokenGrokVersion` / `maybePinBrokenCli`. Which versions, and why: [research/stdio-eof-regression.md](research/stdio-eof-regression.md) and [CHANGELOG.md](CHANGELOG.md) — deliberately not repeated here, per the editing discipline above.

## Build + test

```bash
npm install
npm test         # 4832 tests (215 files), ~20s, vitest — all binary-free (incl. happy-dom DOM tests + fake-CLI ACP integration tests)
npm run test:perf # opt-in session-history perf simulation (NOT in npm test/CI; see § History pagination)
npm run test:integration # real VS Code Extension Host, 59 tests (~40s). NOT part of `npm test`; CI runs it as a second required job.
npm run package  # → all-your-companions-<version>.vsix (`prepackage` deletes EVERY *.vsix, wipes out/, then runs check:vsix)
```

### Test taxonomy — three layers

There are **three** kinds of tests, and it matters which is which:

1. **`npm test` — binary-free unit/DOM/integration suite (4832 tests in 215 files).** Pure logic, happy-dom tests that drive the real `media/chat.js`, a real-shell TerminalManager smoke, and a fake-CLI ACP integration suite (`test/fixtures/fake-grok-acp.cjs`). **Never spawns the real `grok` binary.** Runs in a few seconds with no network, no login, no subscription. This is the floor — every change keeps it green. (Two separate opt-in suites live outside `npm test`: `npm run test:perf` runs the session-history perf simulation — `test/*.perf.ts` via `vitest.perf.config.ts` — and `npm run test:integration` runs the `@vscode/test-electron` smoke below; both are matched only by their own config so they stay out of `npm test`.)
2. **CI — the *same* suite, plus a REQUIRED Electron smoke.** `.github/workflows/ci.yml`'s `test` job runs `npm ci && npm run compile && npm test` on a **matrix of `ubuntu-latest` and `macos-latest`** (`fail-fast: false`; the VSIX is packaged once, on Ubuntu) — **CI's `test` job ≡ layer 1, verbatim** (no `grok` binary, no auth, no subscription, so it *cannot* touch the real CLI — the whole reason layer 1 is grok-free). A second job, `integration`, runs the `@vscode/test-electron` smoke under `xvfb` (`npm run test:integration` — activate the extension, assert commands registered, resolve the webview via the *missing-CLI* onboarding path, then provision `test/fixtures/fake-grok-acp.cjs` through `provisionFakeGrok` so remote resume/`session/load` and matching-sessionId worktree tests run without a real CLI). Test-mode `activate` calls `isolateFromInstalledGrok` before any view can resolve; that latches `testForceMissingGrokCli` so `locateProvider("grok")` will not search config or PATH (an explicit provisioned path still wins). Resume assertions require a distinctive `updates.jsonl` marker to reach the client, `waitForSessionLoad` to settle, and a live ACP session afterward — `initialized` / a reserved session id / replay-before-the-RPC-result are not enough. (`startSession` swallows a failed load and still resolves the reservation.) It's a **required gate** (validated passing against a real VS Code Extension Host before landing; if a Linux/xvfb quirk ever surfaces, fix it rather than demoting the gate). The smoke is still grok-binary-free — it exercises host glue (activation, `getHtml`/CSP, `localResourceRoots`, command registration, hermetic ACP resume) the unit suite structurally can't reach. Compiles in isolation (`integration/tsconfig.json` → `out-integration/`), so it's out of `npm test` and the extension build.
3. **`npm run test:live` — on-demand pre-release suite against REAL grok (`scripts/live-tests.cjs`).** It covers the real handshake, capability drift, prompt/cancel/interject, fork/parallel/restore, plan enforcement, rewind, usage, and generative surfaces. The plan lane now uses native verdicts: its first same-turn `exit_plan_mode` response is `cancelled`, the second is `approved`, and the gate is lowered inside that response callback before implementation continues; `plan-cancel-rewind` uses native `abandoned` with no primer or marker turns. It reuses the compiled dispatch/gate/rewind modules and shipped webview helpers. It needs a logged-in grok and burns credits, so it is run deliberately before a release and never belongs in `npm test` or CI. A SKIP does not fail the gate; research probes remain manual one-offs.

**So:** local `npm test` == CI's `test` job (both binary-free) — but that is NOT all of CI: a second required job runs the equally binary-free Electron smoke, so `npm test` alone is a subset of what must pass. Mirror it locally with `npm run test:integration`. The real-grok tests are a separate pre-release gate — run before a tag/release where a logged-in grok exists, never on every commit.

**Standing test discipline.** Every `session.provider === …` branch has both-provider coverage. A wrapper that assumes a function's documented invariants carries that function's contract tests, including consumed-slot pagination. External-artifact fixtures mirror the real listing and layout, including multi-platform bundles and the Codex package structure. Every new filesystem or network stream has fault-injection coverage for asynchronous error paths.

### grok CLI version + updating

The native-Windows build (`irm https://x.ai/cli/install.ps1 | iex`) installs from the **stable** channel. The extension pins Windows to the supported build (`GROK_STDIO_DOWNGRADE_TARGET` in [src/cli-locator.ts](src/cli-locator.ts); see § Status → Grok CLI compatibility). **grok does not auto-update.** Updating is the explicit `grok update` command: `--check [--json]` checks without installing, bare `grok update` installs the latest on the current channel, `--stable` (default, weekly) / `--alpha` switch channels, `--version <X.Y.Z>` pins a build. `grok update` can only rename the binary when no grok process holds it open (else *"cannot rename locked executable"*), so the extension's update path tears the whole pool down and **awaits each process's actual exit** before updating; on Windows it `taskkill /T /F`-kills the process **tree** (grok backgrounds children that keep the binary locked) and retries once on a lingering lock (`isLockedBinaryError`). Re-run `npm run test:live` after any CLI update — the wire format is the thing that drifts.

## Known limits

A classified quota or rate-limit turn (`classifyLimitError` in `src/limit-errors.ts`) posts a `limitOffer` card — Continue with another connected companion, Wait and try again, or Dismiss — instead of a generic error. Continue never targets another model of the same provider; the switch is a transcript line (`switchTranscriptLine`). There is no automatic failover.

Persistent permission rules (`decidePermission` in `src/permission-rules.ts`) sit between the plan gate and Auto accept / the card. Deny always wins, then last-match-wins; the built-in safety floor cannot be overridden. Empty user rules are a no-op. Checked-in `.grok/permissions.json` is inert until adopted. Settings → Advanced lists every rule, including the floor. Every automatic grant or denial is a `hostNotice` transcript line.

Rewind works for all four companions. Grok uses `_x.ai/rewind/*` when the CLI supports it; otherwise — and for Codex, Claude, and Gemini — the host restores files from client checkpoints (`src/checkpoints.ts`, stored under `globalStorage/checkpoints`). Snapshots are the exact bytes of each workspace file taken before the first write of a turn. A hash mismatch against both the before-image and the recorded after-image is a foreign change and always asks before overwriting. A failed snapshot disables that turn's checkpoint (`hostNotice`) and never aborts the turn.

The Review panel above the composer lists every file this turn or the whole session changed, grouped by path, with `+N −M` matching the sum of the inline diffs. Discard file runs `planEditRevert` (chained in memory for a file edited more than once). Discard all restores the AP-08 checkpoint — never N sequential reverts, which would leave a half-state on conflict. An empty turn keeps the panel off.

A new conversation is **Agent** or **Crew** (`sessionType`, chosen before the first message and locked at it). Agent is today's chat, with optional companion subagents. Crew is a stage-gated workflow: the user types an idea, `idea-to-done` (or another preset) plans / implements / reviews / fixes, and a human gate sits between stages (`src/workflow-run.ts`). Stage sessions are hidden children (`hiddenReason: "crew-stage"`). `/crew` typed in an Agent session offers to open a Crew session (D8) unless `companions.crew.inThreadCommand` is on.

`/agent <name> <task>` runs one named role in its OWN session and returns a card in the calling thread. `/crew [flow] [goal]` (legacy, behind `companions.crew.inThreadCommand`) walks a step list sequentially: the host assigns each step to a role from file types and `when_to_use` (a question card if that is ambiguous), briefs a fresh session per step, and shows a Crew panel above the composer. The flow's `roles:` is the candidate POOL in the flow's own order (`presetRoles`) — past the match rank, that order decides an ambiguous assignment — and `review_every:` splices a review step after every N working steps (`applyReviewCadence`, never as the last step, since the run already ends on the Review panel). Both fields were parsed and ignored before AP-14, which made a crew flow a label rather than a configuration. Both commands are answered by the host and never forwarded to a CLI (`HOST_SLASH_COMMANDS` in `src/slash-filter.ts`). Roles are `.companions/agents/<name>.md` and crew flows `.companions/crews/<name>.md` (`src/agent-roles.ts`, `src/crew-preset.ts`), resolved across three narrowing scopes: five built-ins (`planner`, `implementer`, `reviewer`, `researcher`, `fixer`), then `~/.companions/` (this machine, every project), then the open project, which wins. A project file replacing a global one is an override, not a conflict, and the winner records what it displaced; two files of the SAME scope claiming one name is still reported. **Settings → Agents & Crew** edits both sets: each role's companion, model, effort, mode, scope globs, budget and permission lines, and each flow's role pool, verify command, review cadence and parallel flag. Writes go through `src/agent-role-write.ts`, which emits the frontmatter subset the parsers read (prose as `|` block scalars, so no quoting scheme is invented) and REFUSES any draft that does not survive a re-parse — a page that says "saved" over a file meaning something else is the same quiet lie as a same-model review. The page, its writes and the frame that feeds it are host-local (`OUTBOUND_DISPOSITION`), like the AP-04 rule files. A role's model and effort are applied on the `newSession` path, before the first turn, never with a live `setModel`; a model the role's provider does not carry is a configuration error, not a fall back to the default. Two roles on one provider with different models is a main case. The role receives a deterministic briefing (`src/briefing.ts`) instead of a transcript, and briefs/results/`log.jsonl` live under `<globalStorage>/runs/<runId>/` (`src/agent-run.ts`), not in the repo. Between crew steps, `reconcileFiles` feeds the next briefing with the files the host *observed*, not only the ones the previous role named. A companion that reports plans as prose (Grok) is refused as `planner` rather than started with an empty list. The card states the cost — a role is a second, separately billed run — and measures the role's own "files touched" against the diff blocks the host actually recorded, naming edits the role did not report and files it named that were never edited. The shipped `reviewer` prefers a companion other than the calling session's; when only one is connected it still runs and the card says the review was not an outside opinion. Stop holds the whole crew run, not just the current step. A second claim on the same path is a card (`src/file-claims.ts`, exclusive-create). A role budget is enforced (`src/crew-budget.ts`) with a continue/stop card, never a silent abort. A quota/rate-limit mid-run fails over to the next provider and never retries the exhausted one. Parallelism is opt-in (`parallel: true` on a crew preset): independent writers share a wave, each in its own worktree, capped by the live-session pool (`maxLive` minus unreapable `working`/`needs-you`); sequential is the default. Role `permissions:` lines (`allow edit src/**`) are a tight AP-07 overlay on that role's session — not a blanket auto-accept; Deny and the safety floor still win, and the run ends on the Review panel. The role's edits go through the normal permission and diff machinery.

`/handoff [role]` and `/second-opinion [role]` (AP-11) commission a role the same way, with a task **nobody typed**: the host derives the briefing from the session's own state — the last user message as the goal, the AP-02 plan entries as done/open work, the AP-09 diff paths as files — and never from the transcript (`src/handoff.ts`, pure). Both are also buttons: second opinion on the footer of the turn that just ended, handoff in the review panel's header. The button path confirms first and names the role, provider and model it chose; the typed path does not, because naming the role is what typing it does. **The confirmation carries no cost or token figure** (decision §18.3) — the exact cost on the result card afterwards is the only number about money in the flow, which is why `formatRunCost` must keep saying "no cost reported" rather than a reassuring `$0.00`. A second opinion with nothing recorded to look at is refused before anything is spent. The derived briefing carries a `## Where this came from` section naming every source and, for each empty one, why it was empty — `BRIEFING_FORMAT_VERSION` is 2 for that section, and a v1 run on disk stays readable because the stamp says which shape it is. `structuredPlan` in the AP-01 matrix answers "does this companion report a step list at all": no for grok, yes for Claude and Codex, and a **probe** for gemini, which is one provider id over two CLIs that differ (Gemini CLI reports entries, Antigravity reports prose) — resolved only by a list actually arriving, never guessed, because the guess would be written into every derived briefing as a fact.

Codex image generation is recognized only on a Codex-provider
`kind:"other"` / `title:"Image generation"` call. Completion maps to
`<codexHome>/generated_images/<sessionId>/<toolCallId>.png` only after UUID /
`exec-UUID` validation plus resolved containment, and flows through
`postGeneratedMedia`, giving VS Code, desktop, and remote the same media pipeline
and their normal surface-specific actions. `CODEX_HOME` overrides the platform
home; provider scoping prevents Grok user-derived tool titles from false-matching.

- Live child activity on grok 1.0.3+ is a compact stream inside the parent card (prose, thoughts, tool rows), not a nested inspector of the child's own session. Composer-era CLIs still send no child stream. Cold reload rebuilds cards from the lifecycle rail only.
- Generated media is served only when canonical containment proves it lives under the Grok session root or Codex `generated_images` root; trusted files may use a base64 `data:` URI when the current surface cannot serve that root
- Worktree sessions are created and applied from the gear menu and the Command Palette (`companions.newWorktreeSession` / `applyWorktree` / `removeWorktree`); there is no browser for worktrees that already exist on disk. A live Grok session in this checkout uses `_x.ai/git/worktree/*` (clone mode included); otherwise the host runs local git (`src/worktree-local.ts`) and can only produce a linked worktree. Apply is file-by-file with the same conflict rule as `planEditRevert` — never `git merge`. Grok is never started just to make, apply or remove a worktree.
- The native diff editor is preview-only: it reconstructs full-file context from the file on disk and Grok's replaced-region metadata, but falls back to the region alone if the file is unreadable, oversized, or no longer matches; the write happens via `fs/write_text_file` after approval
- View placement: **default-homed in the Secondary Side Bar** (`viewsContainers.secondarySidebar` — requires VS Code ≥1.106, the `engines` floor; older hosts can't install this build — **Antigravity is on base 1.104** and refuses it, keeping the last compatible version). Relocation is one-click via Settings → Advanced → **Move view** (direct `vscode.moveViews` into the per-location containers — `src/view-move.ts`), or drag. Cursor's primary-side-bar context menu still hides the built-in "Move To" entry — the gear mover is the workaround. User moves persist; a persisted placement wins over the contribution default (*Reset Location* restores the default)

## Cross-platform notes

- `terminal-manager.ts` selects the shell via `resolveTerminalShell(platform, resolve, pref, posixShell)`: Windows runs the agent's commands under PowerShell (`pwsh.exe`→`powershell.exe`, else cmd.exe via `shell:true`) to mirror the standalone CLI (#46); POSIX `auto` uses `$SHELL` when it is an absolute path other than `/bin/sh`, whose basename is in the POSIX-grammar allowlist (`POSIX_SHELL_NAMES` — fish/nushell/tcsh get `/bin/sh`, because `posixSpawnArgv` hands them the agent's POSIX script directly), and which is a REGULAR EXECUTABLE file (a directory named `zsh`, or one with no execute bit, would fail every command with `EISDIR`/`EACCES`); else `/bin/sh`. POSIX spawn is `posixSpawnArgv`: peel grok's `/bin/bash -lc` wrapper (`unwrapGrokBashLoginWrapper`) and `spawn(host, ['-c', script], { shell: false })` so the host cannot exec that wrapper (issue #140; `GROK_SHELL=zsh` alone does not stop grok 1.0.x from sending `bash -lc`). Windows still uses Node `shell:` (`<shell> -c "<command>"`; pwsh + Windows PowerShell both accept `-c`, and Node passes the command string through faithfully; only cmd/bash-style `\"` escaping doesn't, which grok won't emit for a PowerShell target). `whichOnPath` skips the `\WindowsApps\` Store-alias stub. `grok.terminalShell` (`"auto"`|`"cmd"`, host-read → `setTerminalShellPreference`, cache-clearing) is the escape hatch to cmd.exe / `/bin/sh`. Don't hardcode shell paths. **The agent is told which dialect to WRITE for** via `GROK_SHELL` in its spawn env (`buildEnv` in `sidebar.ts` sets it from the pure `grokShellEnvValue(resolvedTerminalShell(), platform)` — `pwsh`/`powershell`/`cmd` on Windows; **never set on POSIX** — upstream builds the model-facing `Shell:` from `$SHELL` on Unix (`resolve_shell_display`) and reads `GROK_SHELL` there as a PATH to a shell binary it validates as executable, so a bare `zsh` never reached the model; running the shell `$SHELL` names IS the POSIX alignment. Never overrides a user-set value): grok's ACP mode otherwise describes the shell from its own host detection and can emit POSIX idioms for a PowerShell host (§2.9; the `Shell:` line in the model's first message tracks `GROK_SHELL`, `research/oss-surfaces-probe.cjs`). POSIX `$SHELL` vs `/bin/sh`: `research/posix-shell.md`. **The `pwsh`-vs-`powershell.exe`-fallback gap is real: Windows PowerShell 5.1 collapses any non-zero native exit to 1 (pwsh 7 preserves it) and rejects `&&`/`||` chains (pwsh 7 accepts them) — install pwsh 7 for full parity.** A fresh shell spawns per command, so the profile re-runs each time (matches standalone's reachable functions, but adds latency and any profile stdout can prepend to captured output; on a `Restricted` execution policy 5.1 skips the profile + warns). The agent only acts on zero-vs-non-zero, which is preserved. Root cause + probe evidence: `research/powershell-terminal.md`.
- `cli-locator.ts` reads `HOME` / `USERPROFILE` env vars first (testability), falls back to `os.homedir()`. Every provider's locator scans PATH through `cli-path.ts` (`findCliOnPath` — PATHEXT on Windows, regular executable files only), and only falls back to a hidden `where` / `command -v`, which is what keeps console windows from flashing. Checks `.cmd`/`.exe`/`.bat` extensions in the Windows home-bin lookup.
- Tests use `node -e "..."` everywhere, so commands are deterministic across platforms — don't add `pwd`, `awk`, `sleep`, `true`, etc.

## Publishing

**Release procedure — ALWAYS tag + create a GitHub Release (with the `.vsix` attached) on a release push to `main`** (standing convention; mirrors the `v1.0.0…` tag history + GitHub Releases):

**What actually happens today in this fork: the release is driven by hand.** The maintainer builds the vsix locally (`npm run package`) and uploads it to **Open VSX through the website**, not through a script. Treat that as the procedure until it is deliberately changed.

`scripts/release.ps1` / `scripts/release.sh` are inherited from upstream and **have not been run in this fork**. They still assume upstream's shape: a real-`grok` `test:live` gate, an `OPEN_VSX_API_KEY` in a root `.env` for `npm run publish:ovsx`, a `desktop-release.yml` dispatch for `.exe`/`.dmg`/`.AppImage` installers, and a `grok-vscode-phuryn-X.Y.Z.vsix` filename that `npm run package` no longer produces. **Do not run them on a maintainer's behalf** — an unreviewed run would tag, push, publish and dispatch workflows in one go. If they are ever adopted here, fix those assumptions first and rewrite this paragraph to say so.

`npm run publish:ovsx` (needs `OPEN_VSX_API_KEY`) and `npm run marketplace:publish` / `marketplace:login` exist as scripts and are likewise unused so far.

The step-by-step procedure:

1. Bump `version` in `package.json` and add the dated section to `CHANGELOG.md`. **The version line is 0.x, so semver's pre-1.0 reading applies: the MINOR is the feature lane and the PATCH is the fix lane.** Concretely — patch (+0.0.1) for fixes, refinements of an affordance that already existed, and doc/test work; minor (+0.1.0) when users gain something they could not do before. The test is what users gain, never how large the diff is or how long it took. **Only the maintainer decides to bump**, and never as a side effect of finishing a feature. (Upstream's rule — "PATCH unless Paweł approves otherwise" — is retired with the fork; there is no second approver here.) As part of this pass, **review the release-facing docs for staleness against what actually ships** — this review is a required step, not optional:
   - `README.md` — features / screenshots / install matrix.
   - **`README.marketplace.md` — the STORE listing, and a separate file.** `npm run package` ships it via `vsce package --readme-path`, so this is what the VS Code Marketplace and Open VSX render; `README.md` is only the GitHub page. Every edit to one is a decision about the other: the two carry the same feature list (keep the ordering in step), but deliberately different heroes — the listing sells the **extension**, so a desktop-app screenshot is off-message there. Its images are absolute `raw.githubusercontent.com/…/main/…` URLs, so **deleting or renaming anything under `docs/screenshots/` breaks the published store page** — remotely, after the release, with nothing local to notice. 3.2.1 shipped exactly that (alt text and a broken-image icon on Open VSX) because only `README.md` was updated. `test/readme-images.test.ts` now fails on a dangling reference in either file; it does not check that the two agree on content, which stays a judgement call.
   - `TESTS.md` — test plan vs. what actually ships.
   - `CLAUDE.md` — the project map (§ Module map, § ACP surfaces, § Known limits, the test-count floor): does it still describe the current architecture? It deliberately **doesn't** hardcode the version (it points to the changelog), so it needs no version edit — but its prose can go stale as behavior changes.
   - `docs/architecture.md` — the architecture doc: keep it in sync with new modules / event flows / surfaces.
   - `package.json` itself — description, `engines`, `categories`, `contributes`.

   Keep `CHANGELOG.md` entries **terse** (1–3 bullets per release under Added/Changed/Fixed; deep detail belongs in commits / `research/`, not the changelog); releases before the current minor live in `docs/CHANGELOG-ARCHIVE.md` (linked from the foot of `CHANGELOG.md`).
2. `npm test` (4540-test floor, all green) + `tsc -p . --noEmit` clean + **`npm run test:integration`** (the real Extension Host, 59 tests — `npm test` is only CI's `test` job, and CI runs this as a SECOND required job; without it a release can be tagged before CI goes red). **`npm run test:live` against real grok** is the third gate where a logged-in grok is available; it burns credits, so run it deliberately rather than reflexively, and say in the release notes if it was skipped.
3. **Repo-hygiene check, then** commit + push to `main` (direct-to-main, no feature branches). Never `git add -A` blind: run `git status --short` AND `git ls-files --others --exclude-standard`, and read the untracked list before staging. Anything machine-specific or agent-local that isn't ignored gets added to `.gitignore` in the same commit rather than committed and cleaned up afterwards — this repo is PUBLIC, so a stray file is published, not just committed. Offenders seen untracked-and-unignored: `.claude/settings.local.json` (machine-specific tool permissions) and ad-hoc `.verification/` output dirs left by an agent. Also confirm nothing under `media/` was hand-edited that a downstream consumer regenerates.
4. **Annotated git tag** `vX.Y.Z` at the release commit → `git tag -a vX.Y.Z -m "Release vX.Y.Z"` → `git push origin vX.Y.Z`.
5. **GitHub Release** for that tag → `gh release create vX.Y.Z --title "Release vX.Y.Z" --notes-file <notes> <vsix>` (notes = the new changelog section(s); include any earlier version that was bumped but never released). **Always attach the `.vsix` that this run of `npm run package` just produced.** Never attach a leftover vsix from an earlier build.
6. **Store publish — Open VSX, by hand, by the maintainer.** The vsix is uploaded through the Open VSX website under the `zfzfg` namespace; no script is in the loop today (§ Publishing intro). The VS Code Marketplace is **not** served by this fork — `publisher` is `zfzfg`, and nothing has been published there.
   - **An agent never publishes.** Building the vsix is fine; uploading it is the maintainer's action.
   - **Never announce a store as "live now."** A completed upload is not public availability — Open VSX scans new versions before listing them. Say **"~10 minutes"** in any user-facing message.
   Publishing ≠ tagging.

7. **Close the loop on every issue the release fixed — this is part of releasing, not follow-up.** For each one: comment saying what shipped and in which version, apply `done-please-confirm`, and leave it **OPEN** (§ Repo conventions — the reporter decides, and `close-confirmed.yml` closes it after 3 quiet days). Sign the comment per § Repo conventions. Sweep the whole open list, not just the issues named in the changelog: a release sometimes fixes something nobody linked, and a slow-performance report may have a cause that is not ours at all — read the thread before crediting a fix to it.

   **Do NOT label before the fix is actually installable.** The label starts `close-confirmed.yml`'s 3-day clock, so labelling while Open VSX still lists the previous version can auto-close an issue the reporter never had a chance to verify — with a message claiming a fix shipped. **The Open VSX listing is the gate**, not the tag and not the GitHub Release. Commenting earlier is fine (it starts no clock) as long as it says where the build can actually be had — the vsix on the GitHub Release is a legitimate answer.

Don't skip the tag/release (or the vsix asset) on a release push. A pure mid-dev version bump that isn't a release is the only exception.

## Repo conventions

- **Work on `main`, synced to `origin/main`.** `main` is the only working line — start every task from `main` fast-forwarded to `origin/main`. The `dev` branch is **abandoned** (stale far behind `main`); do **not** develop on it. If the working tree is on `dev`, or `main` is behind `origin/main`, switch to `main` and `git reset --hard origin/main` before doing anything else (the published version lives on `main` — a stale checkout will look many versions behind and misnumber the changelog).
- Direct-to-`main`, no feature branches
- **Never commit or push automatically.** Changes reach `main`/`origin` only on the user's **explicit** request (rare) or as part of a release. Otherwise: build + reinstall locally for testing and leave the working tree uncommitted.
- Commits explain the *why*, not the *what*
- Don't introduce abstractions speculatively
- Don't add comments that explain what well-named code already says
- **Keep `CLAUDE.md` a current-state map** (see the editing-discipline note under § Status): rewrite changed behavior in place, never append changelog narrative or bug post-mortems here — link `research/*.md` / CHANGELOG instead
- 4540 tests in 200 files is the floor — every PR should keep that green. All tests are binary-free (no CLI spawn); binary-dependent probes live in `research/*.cjs` and are run manually, never by `npm test` or CI
- **Rebuilding clears older `.vsix` first** — `prepackage` deletes **every** `*.vsix` in the repo root and wipes `out/`, then runs `check:vsix` (`scripts/check-vsix-requires.mjs`); `npm run package` then builds `all-your-companions-<version>.vsix` with `README.marketplace.md` as the store readme. (Upstream's `check:relay` / `PRODUCTION_RELAY_URL` gate is gone with the relay — `scripts/check-production-relay.mjs` does not exist here.) After any doc or code change, rebuild + reinstall so the installed extension's bundled docs are current. **Package last:** the vsix bundles `CLAUDE.md`/`README.md`/`docs/` as files, so finish *all* doc + code edits **before** the final `npm run package` + reinstall — otherwise the installed build ships a stale-docs snapshot. If you rebuild mid-task and then touch docs again, rebuild again so the order is always edit-everything → package → reinstall.
- **Version bumps are user-initiated.** Iterate at the current version (rebuild the same vsix and reinstall locally) until the maintainer says to bump and publish. Don't bump `package.json` on your own. On a release, the default is a **patch** bump (+0.0.1); a **minor** is for user-visible new capability, and while the version is 0.x that minor is also the lane for breaking changes (§ Publishing step 1). Never infer the size of a bump from the size of the diff.
- **Releasing requires a direct instruction to release — a version number alone is never one.** Only an unambiguous imperative ("release it", "publish 2.0.3", "run the release script") authorizes the § Publishing procedure. Naming a version in any other role does **not**: *"tell them it ships in 2.0.3"*, *"put this under 2.0.3 in the changelog"*, *"this would be a 2.0.3"* are all scope/labelling statements, and treating one as an authorization ships an unrequested tag, GitHub Release, and Open VSX publish — three externally-visible, effectively irreversible actions. The same applies to a release named inside a larger request: the imperative must attach to *releasing*, not to the work. Default to doing the work, leaving the tree uncommitted, and reporting it as ready to release. **In any doubt, ask** — a one-line question costs nothing next to an unrequested publish.

  **An authorization is spent by the release it authorizes.** "Go" ships that version and nothing after it. A bug report about what just shipped is a report, not a renewal — even when the fix is obvious, even when the feature is visibly broken for the person reporting it, even when the version is a patch and needs no version approval. The two are separate questions: **which number** defaults to patch without asking; **whether to ship at all** never does. 3.17.1 was released on that conflation — an owner-reported break in a release minutes old, urgency read as authority. It happened to be a correct fix, which is luck rather than process: a wrong one would have made two bad releases out of one. The shape to recognise is *"they clearly want this, and they said go recently"* — that is precisely the moment to ask, because it is the moment it feels unnecessary.
- **Never close a fixed issue yourself — label it `done-please-confirm` and leave it OPEN.** When a fix ships, reply saying so and apply that label; `.github/workflows/close-confirmed.yml` closes the issue after **3 quiet days**, and any comment from the reporter removes the label so a human takes over. The label is manual-only — the workflow never applies it, and it strips the label from every closed issue so the label list always reads as the live queue. The point is that the reporter, not us, decides whether their bug is actually fixed. Write the reply to match: *"leaving this open for you to confirm"*, never *"closing"*. (Lost during the 2026-08-15 open-sourcing reorganisation and re-learned on #79, where an agent closed a fixed issue outright; the convention had only ever been recorded in a backlog line and in the workflow file itself, so nothing an agent would read before closing.)
- **A contributor stays visible as a contributor.** Any outside contribution reaches `main` with its author's identity intact, so GitHub credits them on the repo's contributor list and the commit shows their name. Merge so their commit survives — never squash someone else's work into a commit authored by us, and never re-implement a PR as our own change. When we adjust a contribution (fixes, review findings, conventions), add commits **on top** of theirs, or if history must be collapsed, carry `Co-authored-by: Name <email>` using the address on their commits. This holds however heavily we rewrite it: the person who found the bug and did the work earns the credit even when little of the original diff survives. Applies to `grok-remote` too — the same rule lives in that repo's `CLAUDE.md`.
- **Sign GitHub comments.** Every GitHub issue/PR comment posted on the maintainer's behalf ends with a signature on its own final line (italic). Pick by whether the text was actually reviewed before posting: reviewed → `_Written with an agent, reviewed by Collin_`; posted without review → `_Written by Collin's agent_`. Only claim review when it happened.
- **This repo is a fork, and the two identities matter.** `origin` is [zfzfg/all-your-companions](https://github.com/zfzfg/all-your-companions) — the `zfzfg` account is **Collin Lerche**, the maintainer you are working with and the repo owner; unsigned comments from `zfzfg` are his own words. `upstream` is `phuryn/grok-build-vscode` (Paweł Huryn, the original author): a source to pull from and credit, **never** a push target and never an approver of anything here. The published identity is `zfzfg.all-your-companions` (`publisher`.`name` in package.json) — the integration smoke asserts exactly that string, so a rename is a two-file change.
